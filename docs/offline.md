# Offline strategy

Principle 5: after the first load the whole app runs in airplane mode. Decision record: ADR 0003.
Tasks: M1 T3 (precache, atomic install) and T4a (update flow). UI copy and placement: `docs/design/update-notice.md`. The pre-M1 to M1 upgrade path and multi-tab behaviour are T4b (sections below).

## What is cached
- `PRECACHE` in `sw.js` is generated by `npm run stamp` from the shell files: `index.html`, `manifest.json`, `icon-*.png`, `src/**/*.js` (when modules exist) and `fonts/*.woff2`. Licences and `fonts/SOURCES.md` ship but are not cached.
- Fonts are self-hosted (Oswald and Inter, latin subset, variable woff2, SIL OFL 1.1; provenance in `fonts/SOURCES.md`). The app makes no request to any other origin.
- The cache is named `homebody-<VERSION>`; `VERSION` is a content hash of the shell, so every shipped change is a new cache. Never edit it by hand.

## How requests are served
- Install: every `PRECACHE` entry is fetched with `cache: 'reload'` (bypasses the HTTP cache so one release never mixes files) and stored in one `addAll`. If any file fails, the install fails and the previous worker and cache keep running. There is no partial cache.
- Navigations (same origin): the precached `index.html`, whatever the query string.
- Other same-origin GETs: cache first, network if missing.
- Cross-origin and non-GET requests are not intercepted.
- Activate: delete caches whose name starts with `homebody-` and is not the current one, then claim clients. Caches with other names are never touched, because the `github.io` origin is shared with other projects.
- All paths are relative to `sw.js`, so the GitHub Pages sub-path, scope and `start_url` are unchanged.

## Update flow (T4a)
- **The worker never skips the wait by itself.** `sw.js` has no `skipWaiting()` at install. A new release installs, fills `homebody-<NEW>` (atomically, see below) and waits. It takes over only when the page asks, or when every window of the app has closed.
- **Messages accepted by `sw.js`:** `{type:'SKIP_WAITING'}` (the page's Update tap), the legacy string `'skipWaiting'` (what pre-M1 pages send; kept so the first update after M1 can still be applied by old code), and `{type:'GET_VERSION'}`, answered with `VERSION` over the message port (local only, no network).
- **Registration:** `register('sw.js', {updateViaCache:'none'})` on `load` (no `?v=`). A check (`reg.update()`) runs once after register when a worker is already active, and when the app becomes visible again, at most once a minute by timestamp. There is no timer: no `setInterval` polls for updates.
- **Is it really an update?** When a worker is waiting, the page asks both the running and the waiting worker for `VERSION`. Equal versions (for example the identical second worker the browser installs when the registration moves from `sw.js?v=7` to `sw.js`), or a waiting worker that does not answer, produce no notice. A running pre-M1 worker does not answer; that counts as different.
- **Never during a workout.** `hbWorkoutActive()` is true when `wmState` is set or `hb_active_workout` holds a restorable workout (the same test as `wmRestoreIfActive`: it parses and has `exercises`; the key is never deleted by this code), so a workout in another tab counts too. While true, no banner, toast or About line appears. The notice is released when the workout layer (`#wm-overlay`) disappears (a `MutationObserver` on `document.body` children, connected only while a notice is pending; no workout code is edited) or when another tab removes the key (`storage` event). After release it waits at least 4 s and until the toast stack `#m-toasts` is empty, so it never covers "Workout saved". It re-checks `hbWorkoutActive()` when Update is tapped and again at `controllerchange`.
- **Reload only when this page asked.** Tapping Update posts `SKIP_WAITING`; the page reloads on `controllerchange` only if it asked, no workout is active and `reg.scope` is this app's. A `controllerchange` the page did not ask for (updated in another window, or a workout began meanwhile) shows "HomeBody updated / Reload" at the next safe moment instead; it never reloads by itself.
- **Every first show waits.** Whenever the card is due for the first time (after a workout, or on an idle page), it waits at least 4 s and until the toast stack is empty, so a toast never covers it. The button row is pinned to the bottom of the card (only the title and body scroll); the active bottom-nav tab carries `aria-current="page"` and is where focus goes after Later or Escape when nothing had focus (page containers are not given roles or labels).
- **Later.** Hides the notice for this page session. The worker stays waiting and activates when all windows of the app are closed; Profile -> About keeps a quiet "Update ready / Update" line. A plain reload of the only tab does not activate it (Chrome and WebKit): close and reopen.
- **First install.** No waiting phase: the worker installs, activates and claims the open page, which does not reload (the cache is complete before activation, so the next offline open works). The page shows the toast "Ready to use offline" once (not during a workout); Profile -> About always shows Offline: Ready / Setting up… / Not available in this browser, and the running `VERSION` with a Copy button. If the first install fails (the installing worker goes redundant before the page is controlled, or `register()` rejects) it reads "Setup failed, reconnect and reopen" (the row label already says Offline), with a diamond marker instead of the round dot so the state is not colour only. "Setting up…" changes to "Ready" without a reload. An old page that stays open after another window updated keeps showing the version it booted with.
- Layout rules from the built-UI review (docs/design/update-notice.md): the card is `z-index:150` (below every sheet at 200), the empty FAB tray box takes no taps (`#m-fab-tray{pointer-events:none}`, K22), Profile scrolls clear of the FAB, and while Updating the primary button keeps full opacity with taps blocked (`aria-disabled`). `update.spec.mjs` checks these with real touch taps at 375, 390 and 430 px wide, in both themes and with reduced motion on and off.
- **Old code.** Tabs and installed apps still running pre-M1 `index.html` reload on any `controllerchange`, not only after their own Update tap (that is the shipped behaviour), and their banner has no workout check. So the first update after M1 can reload an old page mid-workout. The end-user mitigation is limited and honest: publish when people are unlikely to be mid-workout, and rely on the active workout being saved to `hb_active_workout` as it is logged, so an unexpected reload restores it ("Workout resumed") instead of losing it; anything typed but not yet saved into a set may be lost. This is why T4b (the pre-M1 upgrade test) gates the release.
- **iOS storage (unverified, check on a device).** Safari can evict site storage and caches for sites not used for a long time; an app added to the Home Screen is treated differently, but nothing here guarantees it. The shell is rebuilt on the next online open, but local history is not recoverable once evicted, which is why the backup work (T8) matters. The checklist below includes an offline reopen after some time.
- Known gap: `#m-toasts` has no live region (K21), so the toast is not read by screen readers; the About line is.
- Observed in Chromium: a `GET_VERSION` message in flight to the running worker at the moment a new worker installs deferred an activation that a (hypothetical) `skipWaiting()` in install would otherwise cause, for more than 6 s. So the behavioural test alone cannot prove "no skipWaiting at install"; `update.spec.mjs` also asserts it on the source of `sw.js`.

## Verification
- `tests/e2e/offline.spec.mjs`: after the first load, the browser goes offline (`context.setOffline`); the app reloads, fonts load, a workout is logged through the UI and is in History after another offline reload (also in WebKit); a full session makes zero requests to any other origin, online and offline; stale `homebody-*` caches are removed and an unrelated cache is kept; the cache holds exactly `PRECACHE`.
- `tests/unit/fonts-integrity.test.mjs`: font files match `fonts/SOURCES.md`; no Google Fonts host remains.
- `tests/unit/stamp-sw.test.mjs`: the list is derived and hashed; hostile file names fail the stamp.
- `tests/e2e/update.spec.mjs` (T4a; two builds served from one site directory, `tests/e2e/helpers/deploy.mjs`): a new version waits during a workout (no banner, no reload, old worker still active), appears after Finish only once the toast stack is empty and 4 s after the workout layer closed, and Update reloads into the new version with the finished workout saved; Later keeps the old version and closing and reopening gives the new one; no timer polling and one check per return to the app; first install loads one document, shows the toast and About Ready; both message forms activate a waiting worker without the page reloading; a same-`VERSION` worker raises no notice. Principle 5 is tested at the tap (a workout that starts while the card is up blocks Update, no `SKIP_WAITING` is posted) and at `controllerchange` (a workout that starts before the takeover prevents the reload); both checks and the reset of `requested` after the 10 s restore were mutation-checked (removing any one fails exactly one test).
- `tests/e2e/upgrade.spec.mjs` and `tests/unit/pre-m1-snapshot.test.mjs` (T4b): the pre-M1 upgrade, offline after it, and multi-tab (see the two sections below). The upgrade test simulates airplane mode by setting the browser offline and also stopping the test server: with emulated offline alone, a live server let browser-process service-worker update checks (the `sw.js?v=7` to `sw.js` registration change) leave navigations hanging in headless Chromium. Whether that can happen on a phone is not known; the iPhone checklist covers it. The snapshot test compares hashes always and git bytes when d642b2b is reachable (not in CI's shallow clone).
- An old build for the iPhone check must be served from a different origin than the live app (a LAN or localhost server, or another account's host), never another path on the same `<user>.github.io` origin, because the old service worker's `activate` deletes every cache on its origin.
- Manual checklist on a real iPhone (only a phone or GitHub Pages proves these; Pages' `Cache-Control: max-age=600` must not delay seeing the new `sw.js`, which `updateViaCache:'none'` is meant to ensure):
  1. Install from the Home Screen and open it once online. Wait for Profile -> About, Offline: Ready. If you opened Profile earlier it says "Setting up…" and changes to "Ready" without a reload.
  2. Airplane mode, force-quit, reopen: the app, fonts and history load, and a set can be logged.
  3. Deploy a new release and reopen online: no banner while a workout is active; after Finish and the "Workout saved" toast the card appears and VoiceOver reads "Update ready" and the one-line body ("Reloads HomeBody. Your history is kept.") once.
  4. Tap Update: it reloads into the new version, the About version changes, history is intact.
  5. Repeat with Later, then force-quit and reopen: the new version is running.
  6. Largest accessibility text size with VoiceOver, portrait and landscape: the card covers at most half the screen, the title and body scroll while Later and Update stay pinned and fully visible, and after Later or Escape focus returns to where it was, or to the active bottom-nav tab if nothing had focus.

## First update after M1 (pre-M1 code on the user's device)
Tested in `tests/e2e/upgrade.spec.mjs` against the frozen pre-M1 build (`docs/reference/pre-m1-d642b2b/`, commit d642b2b; kept as `.frozen` files so GitHub Pages cannot serve a runnable old worker).
- **Path.** The old page polls `reg.update()` every 60 s, the new worker installs from the old `sw.js?v=7` URL and waits (no `skipWaiting` at install), the old banner "Update Available" appears (it has no workout check), and "Update Now" posts the legacy string `'skipWaiting'`. The new worker activates, deletes `homebody-v11` (and only `homebody-*` caches), claims, and the old page reloads unconditionally into the new build. A user who reloads first gets the new page under the old worker, which does not answer `GET_VERSION`, so the new notice appears and its Update does the same.
- **Verified:** `vaultfit_v1` is byte-identical before and after; exactly `homebody-<VERSION>` remains; the new page's About shows the new `VERSION`; no second notice after the reload (the page renames the registration from `sw.js?v=7` to `sw.js`, the test proves only that no notice appears; if the browser installs an identical worker it waits, and the same-`VERSION` filter keeps it silent); the app then opens offline, a workout is logged and is in History after another offline reload; the new page makes no request to another origin (the old page does ask Google Fonts, which the test blocks). An active workout (`hb_active_workout`) is restored by the old page ("Workout resumed") and again after the update, with the same content (only the stopwatch's `elapsed` keeps changing while a page runs).
- **Known limitation, mid-workout.** Old code reloads without checking for a workout, and every old-code tab reloads on any `controllerchange`, not only the tab that was tapped. Measured with a workout in a second old-code tab: **survives**: the workout and every set already ticked (saved on each tick), restored with "Workout resumed"; history. **Lost**: in-memory state only: a running rest timer (its sheet is closed after the reload) and a value typed into a field that has not been committed (the app saves on `change`, so a field still being edited). Nothing logged is lost. The mitigation for end users is the existing per-set persistence; publishing when few people are mid-workout helps but is not relied on.
- **Not covered here (needs a phone):** whether iOS fires `controllerchange` on claim in a standalone PWA and keeps `hb_active_workout` across the old reload. See the manual checklist at the end of "Verification" and the T4b plan ("Only a real iPhone can prove").

## Multi-tab (new code)
Tested in `tests/e2e/upgrade.spec.mjs` with two pages of one browser context.
- A workout in tab B holds the notice in tab A (the shared `hb_active_workout` key); when B finishes, A hears the `storage` event and shows the notice.
- An update applied from tab A (or any client) claims tab B, but B does not reload during its workout and shows nothing; after B's workout ends it shows "HomeBody updated" and reloads only on its own Reload tap. A is not reloaded either while any tab has a workout.

## Adding a shipped file
Put it under `src/` or `fonts/`, run `npm run stamp`, commit `sw.js`. A runtime file type (`.html .json .png .js .woff2`) is precached automatically; an unsafe file name makes the stamp fail.

## Install atomicity and response checks
- Install fetches every `PRECACHE` entry first (`cache: 'reload'`), rejects any answer that is not ok or was redirected (a captive portal or a Pages redirect must never be cached as `index.html`), and only then opens `homebody-<VERSION>` and stores the entries. A failure deletes the half-written cache, so no new cache is left and the previous worker stays in charge. `offline.spec.mjs` ("a failed precache fetch...") serves a release with a missing font as 404 and checks exactly that.
- `ignoreSearch` on non-navigation assets is safe because shell assets are content-hashed with the release; a `?v=` never selects a different file.
- Constraint: the redirect check relies on `fetch` following redirects by default (`res.redirected`); it does not detect a same-URL 200 that is an error page, which only a content hash could. Not addressed here.
