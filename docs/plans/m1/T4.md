## Scope
- In: `sw.js`: remove `skipWaiting()` from install; message handler accepts `{type:'SKIP_WAITING'}`, the legacy string `'skipWaiting'`, and `{type:'GET_VERSION'}` (replies with `VERSION` over the message port, no network). `index.html`: one consolidated update banner; announce only when no workout is active; reload on `controllerchange` only when this page asked; check on launch and on `visibilitychange` to visible; register `sw.js` (no query) with `updateViaCache:'none'`; offline-ready indicator; Profile -> About with `VERSION`. Tests, a frozen pre-M1 build for the upgrade test, `docs/offline.md`.
- Out: any logging, `wm*`, `persist*` or storage code; `mToast`; install/precache/activate logic from T3 (reject-redirect, atomic install, `homebody-*`-only deletion stay byte-for-byte); `src/` modules; CLAUDE.md (principle 5 wording stays as is); K20 (shared origin); auto-apply when idle (decision 3: tap or next launch only).

## What exists today (index.html, read in full)
Two banners overlap, both keyed `m-update-banner`:
- **A** (static markup, lines 891-904, + `mShowUpdateBanner/mDismissUpdate/mApplyUpdate` 7725-7740): shown by the first `updatefound` listener when `installed && controller`, sets `mPendingSW`. "Update Now" posts the string `'skipWaiting'` (or `location.reload()` if `mPendingSW` is null); "Later" hides it. No workout check.
- **B** (`showUpdateBanner`, 7756-7787): builds a second banner, but returns immediately because A's element always exists, so B is dead code. Consequence: a worker already `waiting` at launch (the `reg.waiting` branch) shows nothing.
- Also: `register('sw.js?v=7')` on `load`; `setInterval(() => reg.update(), 60000)`; `controllerchange` reloads unconditionally (also on the very first claim, hence the extra reload T3 tests wait for); no check on `visibilitychange`. The existing `visibilitychange` listener (6171) is the wake-lock one and is left alone. The workout state is `wmState` (let, 6315) and key `hb_active_workout` (`wmPersist` 6724; removed when `wmState` is null); `wmRestoreIfActive` runs on DOMContentLoaded (7271). Finish and Cancel both remove `#wm-overlay`, then set `wmState = null; wmPersist()` (7160-7163, 6816-6819).

## Acceptance criteria
Copied from m1.md.
- [ ] e2e: with a workout in progress, deploying a new version shows no banner and causes no reload; after Finish, the banner appears; tapping Update reloads into the new version with the finished workout saved.
- [ ] e2e: "Later" keeps the old version running; closing and reopening the app picks up the new version.
- [ ] e2e: upgrade from the pre-M1 `sw.js` + index.html (from git history) to the new version succeeds with no data loss and the app then works offline.
- [ ] No timer-driven `reg.update()` polling remains.

## Approach
**Step 0 (prerequisite, before any code):** product-designer writes `docs/design/update-notice.md` (placement, copy, states below, aria-live, touch targets, glare contrast); you approve it. No `index.html` edit starts before that. States to specify: update available (Update / Later); "updated in another window, reload" ; offline ready (one-time); About lines (version, offline status, a quiet "Update now" when one is waiting after Later). Banner position matters for one-handed use (the old one is at the top).

**First install (decided):** no `skipWaiting`, `clients.claim()` stays in activate. A first install has no waiting phase: it activates, claims the open page, and the page gets `controllerchange` it did not request, so it does not reload. The first document stays uncontrolled until claimed, which is harmless: the cache is complete before activation (atomic install), so the next offline open works. Offline-ready indicator (smallest): when this page session sees uncontrolled -> controlled, show one existing-style toast "Ready to use offline" (constant string, no persisted flag) and keep an always-true status line in About ("Offline: ready" / "Setting up..." / "Not available in this browser"). Copy and placement are the designer's.

**Announce rule:** `hbWorkoutActive() = wmState !== null || localStorage.getItem('hb_active_workout') !== null` (try/catch). The page ignores a waiting worker whose `GET_VERSION` equals the active worker's (see Risks: renaming `sw.js?v=7` to `sw.js` makes the browser install a second, identical worker). When active, the notice is held; release happens on workout end via a `MutationObserver` on `document.body` that fires when `#wm-overlay` disappears (runs after the synchronous `wmState = null`), so no `wm*` function is edited; and via the `storage` event when another tab removes the key. Tap: re-check `hbWorkoutActive()`, set `requested = true`, post `{type:'SKIP_WAITING'}`. `controllerchange`: reload only if `requested`, `!hbWorkoutActive()`, and `reg.scope` is this app's (`new URL('./', document.baseURI).href`); otherwise mark "reload needed" and use the notice. "Later": hidden for this page session, worker stays waiting and activates when every window of the scope has closed; no timers. Checks: `reg.update()` once after register and on `visibilitychange` to visible (min 60 s apart by timestamp, not a timer; offline rejection swallowed). Register: `register('sw.js', {updateViaCache:'none'})`.

**Multi-tab:** the key is shared through localStorage, so a workout in any tab holds the notice in every tab. Update applied from tab A claims tab B (old page code): B does not reload (not requested), shows "reload needed" at its next safe moment, and never reloads during a workout. Chrome/WebKit do not activate a waiting worker on a plain reload of the only tab, so "Later" means close and reopen.

**Two builds, no real deploy:** one temp site directory behind one `startServer` (one origin, so registration, caches and localStorage persist across versions; two ports would be two origins, which cannot test an upgrade). A "deploy" copies a build's files over the site directory, `sw.js` last (`serve.mjs` reads from disk and sends `no-cache`). Build dirs: the current shell (`listShellFiles` + `sw.js`); a variant (copy with an HTML comment appended to `index.html`, then restamped inside the temp copy with `run()` from `scripts/stamp-sw.mjs`, never the repo); and the frozen pre-M1 build. Pre-M1 = commit `d642b2b` (merge of PR #1, the parent of the T2 merge `91ba1bf`): `sw.js` cache `homebody-v11`, registers `sw.js?v=7`, `index.html` last changed in `151d449`. CI clones shallow, so the test cannot read git; the files are committed as a frozen snapshot (Q6).

**First update through old code:** pre-M1 page + pre-M1 worker -> deploy new -> `reg.update()` from the test (the old 60 s poll is a timer) -> old banner appears -> its "Update Now" posts the string -> new worker (installed from the `sw.js?v=7` URL) activates via the legacy branch -> old page reloads into the new build. Variant: reload first (new page under the old worker), then update via the new banner.

## Tests
All SW tests use `serviceWorkers:'allow'`, a context-level route that aborts non-origin requests, and wait on observable conditions (no fixed sleeps).
- `update.spec.mjs`, AC1: seed a running workout (`hb_active_workout` from the synthetic fixture shape); deploy v2; `reg.update()`; assert a waiting worker exists, `reg.active` is still v1, banner hidden, a window marker survives (no reload). Finish through the UI; banner appears; tap Update; page reloads, About shows v2, the finished workout is in history. Catches reload-mid-workout and a leftover `skipWaiting`.
- AC2: tap Later; assert v1 still running and banner gone; close the page; `expect.poll` opens a fresh page, reads About, closes it, until it shows v2 (closing each time lets the waiting worker activate).
- AC3: described above, in Chromium, with the real fixture history: `vaultfit_v1` deep-equals the seed before and after, `homebody-v11` is deleted, exactly `homebody-<NEW>` remains, no spurious banner after the reload, then `setOffline(true)`, reload, Home renders with history, a workout is logged and survives another offline reload. Tagged `@smoke` for WebKit if it passes there.
- AC4: `addInitScript` wraps `ServiceWorkerRegistration.prototype.update` with a counter; `page.clock.install()` + `runFor` 10 minutes -> 0 calls; a `visibilitychange` to visible -> 1 call. Plus a grep unit assertion that `index.html` has no `setInterval` near `.update(`.
- Extra (proposed, not m1.md ACs): first install loads exactly one document, no reload, toast and About say offline ready; legacy `'skipWaiting'` string activates a waiting worker; `{type:'SKIP_WAITING'}` does the same; two tabs (workout in B holds the notice in A; update in A does not reload B; B reloads only after its workout ends); a same-VERSION worker produces no banner.
- Edited existing tests (the approval of this plan covers exactly these): `sw-register.spec.mjs` drops the `t3-docs` document counter and waits for `navigator.serviceWorker.controller` instead; every assertion stays. `offline.spec.mjs` `firstLoad` drops the `workerStart > 0` condition and the "reloads once" comments, waits for `controller` plus `homebody-<VERSION>` holding every `PRECACHE` entry. No assertion weakened or removed. All T1 goldens (SW blocked) unchanged. The T3 atomic-install test must pass unmodified apart from `firstLoad`.

## Risks
- Renaming `sw.js?v=7` to `sw.js` makes the browser treat the script as new and install an identical second worker that would wait and trigger a false "update" banner; the `GET_VERSION` comparison prevents it and the AC3 test asserts it.
- The first update after M1 runs through old code (old banner, string message, unconditional reload that could hit a workout; unavoidable, tell the user to merge when not mid-workout, as T2 did).
- A tab left on old code after another tab updated runs old JS against new files; harmless today (single file), but T5+ modules make the "reload needed" notice load-bearing.
- Only a real iPhone or GitHub Pages proves: standalone-PWA lifecycle (does a force-quit activate the waiting worker, does `controllerchange` fire on claim), Pages' `Cache-Control: max-age=600` against `updateViaCache:'none'` and `cache:'reload'`, the sub-path scope, true airplane mode after Add to Home Screen, WebKit versus iOS differences. Human check, in the PR: install old build on the phone, deploy, open, confirm no banner mid-workout, banner after Finish, Update loads the new version with history intact, Later then force-quit and reopen gives the new version, airplane mode opens it.

## Stop conditions
Stop, report, and wait for the human if any of these happen:
- The change needs a file outside **Files** above, or a new dependency.
- An existing test has to be changed or deleted to make the new code pass (other than the two edits named above).
- A storage change has no migration, or a migration fails on any fixture in tests/fixtures/legacy/.
- A strength standard, MET value, volume target or other training number would have to be written without a source or documented rationale.
- A new external request, third-party script, notification, health-platform link or data source is needed, or a secret seems necessary.
- Exercise data would have to be retyped by hand rather than extracted or sourced.
- The change makes logging a set take more than two taps, or breaks offline use.
- The 'verify' command is still red after two honest attempts.
- The acceptance criteria turn out to be ambiguous or contradict the spec.
- Any change to workout logging code (`wm*`, `persist*`, `mStartWorkout*`, finish/cancel flow) seems necessary.
- Any path is found where a reload could occur while `hbWorkoutActive()` is true.
- The pre-M1 upgrade test fails, loses or alters a byte of user data, or only passes with a sleep or a retry.
- `docs/design/update-notice.md` is not approved, or the implementation needs a UI the spec does not describe.
- The consolidated banner cannot be built without keeping a second banner implementation.
- The frozen pre-M1 snapshot does not match `git show d642b2b:<file>` byte for byte.
