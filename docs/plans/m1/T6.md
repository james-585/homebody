## Approach
**Engines.** The store keeps its ordered `openEngines` list; `boot` now passes `[idb, local]`. The engine contract gains document-level methods so both engines fit one suite: `readDoc() -> {doc, raw, seq} | null`, `writeDoc(doc, {seq}) -> Promise` (atomic), `readMeta()/writeMeta()`, and optional `snapshot/listSnapshots/getSnapshot/prune` (absent on the localStorage engine, which reports `supports.snapshots:false`). The localStorage engine always keeps writing the v1-shaped blob; the store is the only code that touches either.

**Schema v2 layout (ADR 0002).** Database `homebody`, IDB version 1, stores `workouts`, `records` (`profile`, `personalRecords`, `bodyMetrics`, `userPlans`, `favourites`), `meta` (`schemaVersion`, `seq`, `migratedFrom`, `migratedAt`, `persistAskedAt`, `persistGranted`, `lastBackupAt` reserved for T8), `snapshots`. `save()` = one readwrite transaction: clear and re-put `workouts`, put `records`, bump `seq`, all or nothing. **Deviation to confirm (Q2):** `workouts` is keyed by array index (out-of-line key), not `keyPath: 'id'` as ADR 0002 says. With `keyPath id`, two stored workouts sharing an id (or one with no id) would silently overwrite each other; index keys preserve order, duplicates and shape. Needs an ADR 0002 note by the architect.

**Migration 001 (1 -> 2), pure.** It only sets `schemaVersion: 2` (record shapes are identical; "move into IndexedDB" is the engine's job, not a transformation). Time is passed in. It lives in the migrations section of `hb-storage.js` and is exported as `HBStorage.MIGRATIONS`; `CURRENT_SCHEMA` becomes 2 at boot (`createStore` still defaults to `[]` so the T5 tests keep their meaning). The localStorage engine and the mirror hold v1 text with no `schemaVersion`; the runner lifts it to 2 in memory on each boot, which is idempotent.

**First boot after upgrade.** IndexedDB has no `meta.schemaVersion`. Take the stored source text (`vaultfit_v1`, or the T5 legacy-key adoption, unchanged), run it through the runner, then in **one transaction** write: (1) a snapshot `{reason:'pre-migration', schemaVersion:1, createdAt, keep:true, payload:<source text verbatim>}`, (2) all stores, (3) `meta`. The `meta.schemaVersion` check is repeated inside that transaction, so two tabs booting together cannot both migrate (the second sees the first's commit and just reads). Nothing is marked migrated unless the data and snapshot committed. The localStorage source is left untouched (legacy keys too), so a failed or interrupted migration reruns cleanly on the next boot. The migrated state is read back and compared (workout count and deep equality) before the first save is allowed.

**Snapshots and the way back.** Retention per ADR 0002: the last 5 plus the first pre-IndexedDB one (`keep:true`) until the user deletes it. `snapshots()` returns `{id, reason, createdAt, schemaVersion, bytes}` (no payload). `restore(id)`: refuses while `hb_active_workout` exists (never interrupt a workout); snapshots the current state first (`pre-restore`); runs the payload through the runner (so an old v1 payload lifts to current); replaces the stores and mirror in one transaction; then the store goes read-only until reload, so the stale in-memory state cannot be saved over the restore. Console use: `await HB.storage.restore(id); location.reload()`. `snapshot(reason)` is exposed for T7's pre-import snapshot. On the localStorage engine there are no snapshots; the legacy keys and the mirror are the way back, and `status()` says `snapshots:false`.

**The v1 mirror.** What: after every IndexedDB commit the store writes `projectToV1(state)` (the exact six-key blob and key order `persistSave` writes today, plus one extra key `hbSeq`) to `vaultfit_v1`. Why: rollback. Reverting to a pre-M1 build, or running the pre-M1 `index.html` from a cached tab, reads current history (principle 1; ADR 0002; assumption A4). How long: all of M1; removal needs its own ADR. Order: the mirror `setItem` runs synchronously inside the `save()` call (as `persistSave` has always done, so a tap followed by an OS kill still persists) and the IndexedDB transaction is started in the same call (structured clone happens at `put`, so later mutation cannot leak in). `projectToV1` is pure and does not add `hbSeq`; the writer does. Failure is logged, never surfaced (ADR), and shown as `status().mirror:'stale'`.
**Which copy wins at boot** (the risk with any mirror): each IndexedDB commit stores `seq` in `meta` and `hbSeq` in the mirror. A pre-M1 build rewrites only its six keys, so it drops `hbSeq`. Rule: if the mirror has no `hbSeq`, or `hbSeq > meta.seq` (the OS killed us after the sync mirror write but before the IndexedDB commit), the mirror is newer: snapshot the IndexedDB state (`pre-reconcile`), then migrate and import the mirror. If `hbSeq <= meta.seq` the mirror is stale (a mirror write failed earlier): ignore it, rewrite it on the next save. Either way both copies are recoverable. Size cost: about 260 KB of localStorage for the fixture (about 5% of a typical 5 MB budget; 520 KB if a legacy key was also adopted, as in T5). Growth is about 450 KB/year, so the mirror becomes the first quota to bite on a very long history; that is a reason to retire it later, not now.

**Fallback and failure.** IndexedDB missing, `open` error (some private modes), `blocked`, or no answer within 1.2 s (shorter than the 1.5 s `hb-booting` failsafe, so the engine is chosen before the UI appears): use the localStorage engine for this session, `status()` reports `engine:'localStorage', fallback:'idb-unavailable'|'idb-timeout'`, and a late-opening connection is closed and ignored. Because the localStorage engine writes an unmarked blob, the rule above imports it on a later IndexedDB boot (with a snapshot), so a fallback session's work is never discarded. Write failure on IndexedDB (quota, abort, `DataCloneError`): transaction rolls back, the existing retry-once-then-bar path runs (fixed strings by kind, no new copy), and the sync mirror already holds the latest state if it fit. `onversionchange`: close the connection, lazily reopen on the next save; if that fails the normal failure path runs. No new UI; no new bar kinds (an unmapped kind uses the existing "unknown" string). Corrupt IndexedDB (stores present, no valid meta) or `meta.schemaVersion` above current: load empty, read-only, never written, as in T5; "Export saved file" still reads the mirror text.
Not handled, recorded as K31: two open tabs both saving is last-write-wins (as today); detecting a stale tab is a later feature.

**Sync call sites and speed.** `persistSave()` stays synchronous and returns `HB.storage.save(...)`; the 17 call sites and the shim are untouched. `save()` already serialises at call time and coalesces (latest payload wins); queued payloads are held as text and parsed when pumped. Logging a set calls `wmPersist`, not `persistSave`, so the log path is unchanged by T6a. `persistSave` now also starts the transaction (150 clones); measure its synchronous part against `main` (median of 20) and report; stop if it exceeds 16 ms on the fixture.

**Cold start.** The simple path awaits `open` plus one read-only transaction over all stores, started at the top of `hb-storage.js`. Budget +10% of `main` (first visible frame was about 120 to 140 ms, so about 13 ms; IndexedDB open may not fit). Measure first (interleaved, median of 5, `hb:rendered` mark, one-off A/B against `main` in a worktree reported in the PR, plus a generous in-repo absolute budget, as in T5). If it fails after the single-transaction read, the contingency (needs Q4) is a **confirmed-mirror fast path**: boot synchronously from the mirror when `hbSeq === hb_storage_meta.idbSeq` (written after each IndexedDB commit, so both copies are known equal), open IndexedDB right after first paint, and take the slow path above otherwise.

**Folding K25 and K29.** K25 (T6b): `saveActive(json|null)` writes `hb_active_workout` to localStorage **synchronously** (survives a kill; ADR 0002 keeps it there), publishes success or failure, so the save-problem bar now clears on its own when a later automatic write succeeds (the K25 gap). `wmPersist` and the `WM_KEY` removal call it when `window.HB` exists and fall back to today's direct code otherwise (pre-load window). The edit is confined to `wmPersist`'s body. K29: the `wmPersist` and `WM_KEY` coverage is folded in via T6b; the engine timeout ordering above shrinks the pre-load window. **Deferred, K29 stays open and reduced:** `hb_milestones` writes (no history in them) and a "still loading" state for a late script, because the latter is UI (T8, designer spec). K30 stays with T7/T8.

**Delete-all key list.** The code gets one frozen list, `HBStorage.KEYS` (localStorage: `vaultfit_v1`, `homebody_v1`, `homebody_v0`, `vaultfit_v0`, `hb_storage_meta`, `hb_active_workout`, `hb_milestones`, `hb_theme`, `hb_seen_guide`, `hb_seen_tutorial`; IndexedDB: database `homebody`). A test records every key written during a full fake session and asserts it is on the list. `docs/security.md` is updated: IndexedDB rows in the data table (live stores, snapshots, mirror, and that snapshots are extra on-device copies of health data), delete-all must `deleteDatabase('homebody')` after closing the connection and stopping queued writes, and the "what stays" note. `hb_storage_meta` is read once into IndexedDB `meta` on migration and left in place (never deleted).

## Stop conditions
Stop, report, and wait for the human if any of these happen:
- The change needs a file outside **Files**, a new dependency (no `idb`, no `fake-indexeddb`), or an ADR deviation beyond Q2.
- An existing test has to be changed or deleted beyond the two listed edits (`MIGRATIONS` line, helper re-exports); this includes the migration harness or T5 store tests.
- A migration fails any fixture, or any workout, set, PR or profile value differs after migration.
- Any user data, legacy key, snapshot, or stored blob would be deleted, truncated or overwritten without a snapshot first, including in fallback, reconcile and restore paths.
- Any change to the `vaultfit_v1` shape beyond the additive `hbSeq`, or a storage key not on `KEYS`.
- Cold start is over +10% after the single-transaction read and Q4's contingency is not approved; or `persistSave` sync cost is over 16 ms.
- The change makes logging a set take more than two taps, adds latency to the log path, or breaks offline use; a `wm*` edit outside `wmPersist`.
- A new external request, third-party script, or any visible UI is needed.
- The `verify` command is still red after two honest attempts.
- The acceptance criteria turn out ambiguous or contradict the spec (AC5's "Profile -> Data" is already flagged).
