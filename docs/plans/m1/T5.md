## Approach
**0. Prerequisite (T5b only):** product-designer writes `docs/design/write-failure-banner.md` and James approves it in chat before any banner edit to `index.html`, as for T4. It must specify: copy, placement (a top bar avoids the bottom update card at z 150, the FAB tray at 9600 and K22/K23), states (not saved and retrying; Retry in progress; saved, auto-dismiss; and the two load-time variants "saved data could not be read" and "saved by a newer version, saving paused"), `role=alert` once, 48 px targets, contrast, z-index versus sheets (200), the update card (150) and toasts (9950), and the explicit exception to "nothing during a workout" (this banner must show mid-workout). Note for the designer: call sites show success toasts ("Workout deleted") after `persistSave()`; the banner is the only truthful signal. T5a does not wait for the spec.

**1. Boot order.** Today: one classic script, then `DOMContentLoaded` -> `mLoadTheme, persistLoad, mRenderHome, mRenderProgress, wmRestoreIfActive`. New: the classic script is unchanged except that the handler body becomes `function hbStart()` (guarded to run once), and `<script type="module" src="src/boot.js" onerror="hbBootFailed()">` goes after it (deferred, so `hbStart` already exists). `boot.js` builds the store on `engine-local`, `await store.load()` (the localStorage engine resolves in microtasks; nothing slow such as `persist()` or `estimate()` is awaited on the boot path), publishes a frozen `window.HB`, then calls `hbStart()` from the `DOMContentLoaded` event. (Correction, 2026-11-01: a module with top-level await DOES hold DOMContentLoaded in Chromium, so `boot.js` uses a promise chain with no top-level await and waits for the event.) `persistLoad()` stays synchronous and copies the already-loaded document into `state` with today's field-by-field logic. **First paint:** a one-line inline script in `<head>` sets `html.hb-booting`; CSS hides the body until `hbStart` ends (`finally` removes it) and a 3 s failsafe removes it regardless, so there is neither a flash of the empty Home nor a stuck blank screen. A frame-sampling e2e proves no visible frame precedes `hbStart`. **Boot errors:** `store.load()` is given an ordered engine list (just `engine-local` now; T6 puts IndexedDB first). If the engine cannot open (for example `localStorage` access throws in a locked-down browser) the store starts with an empty in-memory state, `status().error` is set, saves fail visibly and the app still starts. If the module graph itself fails to load, `hbBootFailed()` removes the hiding class, starts the app on empty state, makes every `persistSave()` a visible failure, and never writes (so the stored blob cannot be overwritten with empty state). Nothing is ever silently dropped.

**2. Shim semantics.** `persistSave()` stays synchronous and returns `HB.storage.save(payload)`, building the same six-key object in the same order as today and stringifying it **at call time**, so later mutation cannot leak into the write. Call sites are unchanged: they ignore the returned promise, and the shim adds `.catch(() => {})` because failure is surfaced by the store, not by the caller. `save()` resolves on success and rejects after the failure is published (T7 will `await` it). **Ordering:** one writer at a time. Idle: the write starts synchronously inside the call (`engine-local.write` calls `setItem` immediately, as today, so a tap followed by a kill still persists). Busy: the latest serialised payload replaces any queued one (coalescing); when the write ends the queued payload is written; every caller's promise settles when a write containing its data or newer finishes. Last write wins; this matters for T6's async engine, and the fake async engine in the unit test proves it now. **Failure:** retry once (after a short delay); classify (`quota` for `QuotaExceededError`, code 22, Firefox 1014; `unavailable`; `unknown`) and expose only the kind, never the raw message. Retry from the banner calls `persistSave()` again, so it saves the current in-memory state.

**3. Legacy keys and "snapshot".** In schema 1 on localStorage the snapshot is the legacy key itself, left in place: zero extra code and no deletion. Rule as today: only when `vaultfit_v1` is absent, adopt the first of `homebody_v1`, `homebody_v0`, `vaultfit_v0` that has data (treated as schema 1) by writing it to `vaultfit_v1`; **never `removeItem` it**. If `vaultfit_v1` exists, legacy keys are neither read nor touched. Cost: the data is stored twice once, about 2 x 260 KB = 520 KB for a fixture-sized history (about 10% of the usual ~5 MB origin budget; ADR 0002 accepts ~0.5 MB). Quota failure during adoption: `setItem` is atomic per key, so nothing is half-written; the app runs on the legacy data in memory, the legacy key is untouched, the failure banner shows, and the next boot adopts again. The store never frees space by deleting anything (principle 1); the user's way out is Export. A real pre-IndexedDB snapshot registry comes with T6.

**4. Runner and the two todo tests.** `migrate.js` exports a pure `runMigrations(list, doc, {current})` with the harness's semantics (absent `schemaVersion` = 1, ordered by `from`, input never mutated, throws if a step does not set `to`) and refuses rather than guesses: invalid JSON -> `{ok:false, reason:'corrupt'}`; `schemaVersion` above `current` -> `{ok:false, reason:'future'}`. The list is **empty**, `current` is 1, so stored data is bit-for-bit what `persistSave` writes today. On `corrupt` or `future` the store loads empty in memory, goes read-only (`save()` rejects with that reason), and **never writes the original key**; the matching banner variant explains. The two `todo` tests at the end of `tests/unit/migrations.test.mjs` (T1 plan: waiting for the runner) become real tests in place, driving the store with fake storage: the stored string is byte-identical afterwards, and nothing is written. A parity test also runs the real runner and the harness's `applyMigrations` over every fixture (and the harness's lossy fakes), so the harness validates the real runner, not a copy.

**5. Persistent storage.** After the first successful save whose payload has at least one workout, if the sidecar key `hb_storage_meta` has no `persistAskedAt`, call `navigator.storage.persist()` once from that success path, then store `{persistAskedAt, persistGranted | 'unsupported' | 'error'}`. `status()` returns `{engine:'localStorage', persisted, persistAsked, lastBackupAt:null, error?}`, where `persisted` is refreshed from `navigator.storage.persisted()` after boot (never awaited at startup). Time comes in through an injected `now()`; only `boot.js` wires `Date.now`.

**6. `index.html` edit scope (precisely).** (a) one `<head>` inline script + one CSS rule for `hb-booting`; (b) `persistSave`/`persistLoad` bodies replaced by the shims, `STORAGE_KEY`/`LEGACY_STORAGE_KEYS` consts kept only if still referenced; (c) the DOMContentLoaded block renamed `hbStart` plus `hbBootFailed`; (d) the `<script type="module">` tag; (e) T5b: banner markup, CSS and a ~30-line subscriber that renders it with `textContent`, Retry -> `persistSave()`, Export -> existing `mExportData()` (it exports in-memory `state`, so unsaved work is exportable); (f) pending Q3, one line in the `catch` of `wmPersist`. Nothing else. Then `npm run stamp` (new `src/**` files are hashed and precached automatically).

**7. `window.HB` surface added** (T13 documents): `HB.storage.{save, status, subscribe, loaded}` (`loaded()` serves `persistLoad`, `subscribe` serves the banner). Not added: `snapshots`, `restore`, `io`, `exercises`, `release`.

## Stop conditions
Stop, report, and wait for the human if any of these happen:

- Any change to the stored format of `vaultfit_v1`, or any storage key other than `hb_storage_meta` added.
- Any user data, legacy key or stored blob would be deleted, truncated or overwritten (including on corrupt/future blobs and failed adoption).
- A strength standard, MET value, volume target or other training number would have to be written without a source or documented rationale.
- A new external request, third-party script, notification, health-platform link or data source is needed, or a secret seems necessary.
- Exercise data would have to be retyped by hand rather than extracted or sourced.
- The change makes logging a set take more than two taps, adds measurable latency on the log path, or breaks offline use.
- The 'verify' command is still red after two honest attempts.
- The acceptance criteria turn out to be ambiguous or contradict the spec.
- Any call-site edit beyond the shims (the 16 `persistSave()` calls; grep counts 17 lines including the definition, the brief says ~17), or any `wm*`/`mConfirmImport` edit beyond what Q3 approves.

## Risks
- Async boot reorders init: held by goldens, the frame sampler and the failsafe.
- Known gap, found while planning: `wmPersist` swallows its own write errors, so a full quota during a workout is silent until Finish (new K25, see Q3).
- Unknown fields in a stored blob are dropped on the next save (same as today, since `persistSave` writes six keys); the future-version guard covers the dangerous case.
