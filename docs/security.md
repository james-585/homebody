# Security and privacy notes: on-device data (storage)

Status: first version written by storage-sync-engineer during T5; **reviewed by security-reviewer for T5 and T6a (PASS on 56403fc, 2026-11-03) and for T6b (PASS on 89ce707, 2026-11-03)**; later changes still need review (the reviewer agent is read-only). Scope today: what HomeBody keeps in the browser, how it is protected from loss and overwrite, and what a "delete all my data" feature must remove. Principles: CLAUDE.md 1, 4, 8.

## Storage inventory (everything the app keeps on the device)
| Where | Name | Holds | Notes |
| --- | --- | --- | --- |
| IndexedDB | database `homebody`, stores `workouts`, `records`, `meta` | The live data (schema 2): workouts, personal records, body metrics (health data), plans, profile, favourites; `meta` holds `schemaVersion`, `seq`, `migratedFrom`, `migratedAt`, `writer` (random, per session, IndexedDB meta only; not in the mirror, sidecar, snapshots or exports; tells this tab's own late retry apart from another tab's commit), `mirrorSig` and `mirrorSigSeq` (fingerprint of the migrated mirror text and the seq it was current at), `persistAskedAt`, `persistGranted`, `lastBackupAt` (reserved) | T6. Never rendered; a restore payload goes through the migration runner |
| localStorage | `vaultfit_v1` | The v1 **mirror** of the live data: exactly the six-key blob `persistSave` has always written, plus one ignorable key `hbSeq` (the commit counter) | Written synchronously on every save so a pre-M1 build (rollback) reads current history. Not used: sessionStorage (the tests only), cookies. IndexedDB holds the data since T6 (rows above). No network storage, no accounts, no analytics.

## "Delete all my data" rules (for T8 or whoever builds it)
- Remove the listed localStorage keys **one by one**. Never `localStorage.clear()`: the github.io origin is shared with other projects (K20).
- Delete only caches whose name starts with `homebody-`. Unregister only the service worker whose scope is this app.
- Before deleting: stop the `wmPersist` tick (it re-creates `hb_active_workout` through `saveActive`, which is never gated), and stop any pending store retry or queued write (it would re-create `vaultfit_v1`). Delete, then reload.
- The key list is in one place in the code: `HBStorage.KEYS` (`localStorage`: every key above; `indexedDB`: `['homebody']`), covered by a test that records every key written in a full fake session.
- IndexedDB: close the store's connection, stop queued writes (as above), then `indexedDB.deleteDatabase('homebody')` and wait for it to finish (a connection left open makes it `blocked`). Deleting the database removes the live stores **and** every snapshot. `hb_storage_meta` is read once into IndexedDB `meta` and left in place, so delete it too. Delete the `vaultfit_v1` mirror: it is a full copy.
- Stop other tabs first: a second open tab can recreate the database after it is deleted (K32). Until T8 adds a stop-other-tabs step, delete-all must say to close other HomeBody tabs.
- Tell the user what stays: exported `.vaultfit` files and the raw `.txt` file are in their Downloads and the app cannot remove them; and a persistent-storage grant from the browser (`persist()`) cannot be withdrawn by the app.

## Raw "as found" export
`Export saved file` (shown when saved data cannot be read, is from a newer version, or storage failed to open) downloads the stored text of `vaultfit_v1` unchanged. It is read-only (never parses or writes), uses a `text/plain` Blob and the fixed filename `homebody-saved-data-as-found.txt`. It contains health data, so the user should treat the file as private. The plain `Export` beside it exports in-memory state (see K30).

## Protections against overwriting or losing data
- Corrupt or newer-than-known stored data: the store loads empty in memory, goes read-only and never writes `vaultfit_v1`.
- `hbLoadedOk`: `persistSave` refuses to write until `persistLoad` has copied the stored document into state this session, so a storage script that loads late cannot overwrite saved data with the empty startup state. If the storage script fails to load or throws before the store exists, `hbBootFailed()` starts the app on empty state and nothing is written. `wmPersist`, the `WM_KEY` removal and `hb_milestones` writes are not covered (K29).
- IndexedDB (T6): migration and every save are single transactions (all or nothing; tested with an abort part-way). The first migration commits a verbatim snapshot of the source text in the same transaction as the data and the schema marker, so nothing is marked migrated without its way back. The source and the legacy keys are never modified by the migration. `restore(id)` refuses during a workout, snapshots the present state first, and then the store is read-only until reload.
- Which copy wins at boot: a mirror with no `hbSeq` (a pre-M1 build or a localStorage fallback session wrote it) whose fingerprint is not `meta.mirrorSig`, or with `hbSeq` above `meta.seq`, is newer: IndexedDB is snapshotted (`pre-reconcile`), then the mirror is imported and the mirror is restamped. A mirror below `meta.seq` is stale: IndexedDB wins and the mirror is rewritten from it. The decision is one pure function, `decideBoot`, tested as a table. A corrupt or newer-than-known mirror is ignored and left as found. Corrupt IndexedDB (data without valid meta) or `schemaVersion` above the app's: read-only, never written. This is enforced twice: by the `canWrite()` gate in the store (including a save queued before IndexedDB attached), and, since the second review, inside every write transaction, which re-reads `meta` and aborts with `future` or `corrupt` (the store then locks) instead of replacing newer or unreadable data, even if another tab changed it after this tab loaded. `restore` and the import path have the same check (every engine write goes through one `canWrite()` gate, and nothing clears a read-only state); the load-time bar shows (also after a fast boot, which renders from the mirror first); `Export saved file` still reads the mirror text.
- IndexedDB unavailable, blocked, erroring or silent for 1.2 s: the localStorage engine runs the session (`status().fallback`), and its unmarked blob is imported (with a snapshot) on the next IndexedDB boot. A connection that opens late is closed. `onversionchange` closes the connection; the next save reopens it. A fallback session on a marked mirror known to be older than IndexedDB (its `hbSeq` below the sidecar's `idbSeq`) is opened read-only (the existing "Saving is not working" bar) instead of writable, so it cannot write stale data as the newest. The localStorage engine's saves in a fallback session DO rewrite `vaultfit_v1` as unmarked plain text. If `attach()` gives up (8 s), the work it abandoned is cancelled: it can no longer change state, the mirror or the sidecar, so it cannot overwrite what the fallback session saved.
- Fast boot assumption: the page may render from the mirror before IndexedDB opens only when the mirror is provably not older (`canFastBoot`: marked and equal to the sidecar's `idbSeq`, or unmarked with no commit ever noted). If IndexedDB then turns out newer, the store goes read-only (bar: "Saving is not working", reopen) and nothing is saved over it. Every write also checks `meta.seq` inside its transaction (`expectSeq`): if another tab committed meanwhile, the state being replaced is first kept as a `pre-overwrite` snapshot. Every document write (save, migration, import, restore) sets or clears `writer`, so another tab's import or restore is never mistaken for this tab's retry; `meta.seq` never goes backwards. Work that finishes after a timeout must not write the mirror or the sidecar (cancel token plus a guard on both writers; tested with a delayed commit). An import is skipped and decided again if IndexedDB changed during boot (at most two passes, then the localStorage fallback). A mirror whose `hbSeq` equals `meta.seq` is trusted as equal, which is the collision limit of the K31 class.
- Retention is per snapshot reason (newest 5 of each, plus the `keep:true` one); a restore never prunes the snapshot it restores from. Snapshots keep deleted records (K33). Stored reasons are a closed set (`pre-migration`, `pre-reconcile`, `pre-restore`, `pre-overwrite`, `pre-import`, `manual`); anything else is stored as `manual`. `pre-reconcile` snapshots are not pruned until T8 ships a visible restore (K33, K38).
- A failed mirror write is logged and shown as `status().mirror: 'stale'`, never as a save error; the IndexedDB commit is the save.
- Legacy keys are copied, never removed. A quota failure while adopting leaves everything intact.
- The sidecar `hb_storage_meta` is ignored if 1 KB or larger, or if it is not a plain object; unknown fields are dropped; no prototype pollution (tested).
- Failure messages shown to the user are fixed strings chosen by error kind; raw exception text is never rendered.

## `navigator.storage.persist()`
Requested once, after the first successful save whose payload contains at least one workout, and not before. The result and a timestamp go in `hb_storage_meta`; `HB.storage.status()` returns `persisted`, `persistAsked` and `persistGranted`. Some browsers (Firefox) may show a permission prompt at that moment. The request sends nothing off the device.

## Exports leave app control
`.vaultfit`/JSON exports and the raw `.txt` file are ordinary files in the user's Downloads. Once exported they are outside the app's protection and may be synced or shared by the OS.

## Content-Security-Policy (not adopted)
There is no CSP. Adopting one would need hashes or nonces for the inline boot script in `<head>` and the inline `onerror` attribute on the storage script tag (replace with `addEventListener`), plus the many inline handlers in `index.html` (K15, K20).

## Import path (T7a; the UI is T7b)
Status: written by storage-sync-engineer, **not yet reviewed by security-reviewer** (the plan was reviewed twice). The only way a file reaches the data is `HB.io.importFile(file)` then `apply()`:
1. **Size before parse:** `file.size` over 20 MB (`IMPORT_MAX_BYTES`, equal to `LIMITS.maxBytes`, asserted by a test) is refused before `file.text()`; `validate` checks `text.length` again. A single leading BOM is stripped.
2. **Parse in try**, no reviver. Top level must be a plain object with `_vaultfit === true`; `_version` an integer (absent counts as 1), above the app's schema refused; older versions are validated, lifted by the migration runner, and validated again.
3. **Whitelist copy, every kept leaf checked** (`src/storage/validate.js`): values are copied by name into fresh objects (no `Object.assign`, no setters from parsed objects); unknown keys are dropped and counted, including `schemaVersion`, `seq`, `hbSeq` at any level and `_name`; dictionaries (`personalRecords`, `_progressionLog`, equipment) refuse `__proto__`, `constructor`, `prototype` and are built with `defineProperty`. Exact types for every field that reaches an unquoted `onclick` or a class name: workout ids safe integers, plan ids finite numbers in (0, 2^53], enums for level/goal/sex/activity/trackType/unit, finite ranged numbers elsewhere. Dates: strict ISO-8601 regex then a window (2000-01-01 to now + 366 days; later than now + 1 day is counted as a warning); `Date.parse` is never used.
4. **String rule:** name-like fields (workout, exercise, plan, day and profile names, favourites, `personalRecords` keys, `_progressionLog` keys, `author`) refuse `<` and `>`; notes (workout `notes`, plan `desc`, day `note`) allow them (they only reach escaped text sinks; record that sink as text only). Both refuse C0/C1 controls (keeping `\n` and `\t`), U+2028/2029, bidi overrides and isolates and lone surrogates; nothing is silently stripped. Allowed: apostrophe, double quote, backslash, backtick, `&`, parentheses, emoji, every script. Caps: names 500, notes 20,000 (import only; input limits are T8). Also refused in every string: U+200B to U+200F, U+061C, U+FEFF inside a string and U+FFFE/FFFF (invisible and direction characters that can disguise a name; this also refuses zero-width joiners in emoji sequences and Persian/Indic text, a known cost). **Display-only values** (profile goal, sex, activity; plan goal, level) accept the shipped values and also any token matching `^[a-z][a-z0-9_]{0,39}$` (safe as text and as a class name), reported as `warnings.unrecognised` with record paths, never values; `trackType`, PR `unit` and `side` stay strict enums.
5. **Bounds:** workouts 20,000, exercises per workout 100, plans 200, plan days 100, exercises per day 100, body rows 20,000, PRs 2,000, favourites 1,000, progression log 5,000, equipment lists 100. Depth is bounded by the schema (only known paths are walked).
6. **One invalid record rejects the whole file.** A refusal is `{reason, where}`: a fixed reason code and a record path made of names and indices; never a value from the file, never a dictionary key's text (keys appear as `[key N]`). At most 20 problems are listed.
7. **Apply** (`store.importDoc(text, {mode})`, mode `merge`, `replace` or `plans`) ALWAYS validates the raw text itself (there is no "already validated" input), then **drains first** (`settled()` until nothing is in flight or queued, so a save accepted just before commits and is in the merge and the snapshot), **checks and takes the lock in the same synchronous block** (read-only kind `importing`; a save during an import is refused), settles again, re-checks the active workout, reads what IndexedDB holds NOW (an empty database is read as "expect empty", so another tab's first-ever commit is a mismatch too), merges against that (never against the caller's in-memory state), and writes data, a `pre-import` snapshot and meta in ONE transaction with `expectSeq` and `skipOnMismatch`: if another tab committed since the read, nothing is written and the user is told to preview again. The lock is released on every failure path; a failed import leaves the store writable. `seq` comes only from the store. Refused: while a workout is active, when the store is read-only (corrupt, newer, restored), on the localStorage fallback engine (no snapshots), when the lazy module fails to load or its version differs (`io-unavailable`, `io-skew`; there is no fallback to any older import path), and Replace with a `_partial` file.
8. **Merge is the default** (it only adds; yours win ties; a workout is a duplicate only against current data, by date, name and exercises; ids are unique in the result and re-id'd within the safe-integer range); **Replace** takes the file whole. Undo is `restore(snapshotId)` (own `pre-restore` snapshot), offered cleanly only while IndexedDB's `meta.seq` (read at tap time) still equals the import's commit; otherwise it needs `acceptLater`.
9. **Lazy modules:** `src/storage/validate.js` and `import-export.js` load with `import()` on the first Import or Export, from the URL of `hb-storage.js` (captured from `document.currentScript` at first run), precached by the service worker, so they work offline. `file://` is unsupported (no module loads, import refuses). The modules never log imported content and export an API version and the schema they were built for; `HB.io` checks both.
10. **Preview and result text are rendered from `summarize` output only** (numbers and clipped strings, text nodes). T7b rewrites `mShowImportConfirm` and `mImportPlanOnly` to do so; until it merges, the shipped preview is the live XSS (see Open items).

### Sink inventory (T7b step 1, not done in T7a)
Every `onclick`, attribute, `style` and `innerHTML` sink an imported string can reach must be listed here and shown safe in its own context before the UI is wired. Method: grep `innerHTML|outerHTML|insertAdjacentHTML|on[a-z]+="` plus the `mToast` sink (~1138). **Rule: `escHtml` does not escape `'`, so its output is safe only in HTML text and double-quoted attributes. It and `.replace(/'/g, ...)` are insufficient inside inline handlers, because attribute values are entity-decoded (`&#39;`) before the JS parser runs.** The safe pattern already in the file is `data-name="${escHtml(name)}"` with `onclick="f(this.dataset.name)"` (index.html ~2059). Known sinks to fix in T7b: the favourites list (~5755, 5756) and `wmShowExInfo` (~6521). The plan-day note sink (~4501) is escaped text. Numbers that reach unquoted handlers are safe because the validator types them.

## Mirror ceiling and counters (T7a)
- **One gate** (`mirrorText` in `src/hb-storage.js`) is called by every mirror write: `stampMirror`, `renumberMirror`, `restampMirror`, the save path (including provisional plain writes) and the boot `rewriteMirror`. It refuses a text over 512K characters (`MIRROR_CEILING`) or a counter that is not an integer in [0, `MAX_SEQ`]. When it refuses, the existing mirror is left as it is (marked, `hbSeq` at or below IndexedDB's), `status().mirror` becomes `'stale'`, and a provisional save over the ceiling writes no plain text. **Excluded on purpose:** the localStorage fallback engine's own `write`/`writeDoc` and the legacy-key adoption, where refusing would drop the only copy.
- **Provisional saves:** a save made before IndexedDB attaches (fast boot) over the ceiling writes no plain text, so that edit exists only in memory until attach commits it (a window of milliseconds to the 1.2 s timeout); a kill inside the window loses it (K42).
- **Consequences:** a user above about 1,500 workouts stops updating the mirror (K42). A pre-M1 build then shows older data; if data is saved there, the next M1 boot lets that unmarked mirror win over IndexedDB and the newer data survives only in a `pre-reconcile` snapshot, with no UI to reach it until T8. **A stale mirror (over the ceiling or ignored as corrupt) keeps deleted records in plain localStorage:** delete-all must remove `vaultfit_v1` and the legacy keys whatever the mirror's state.
- **Counters (K39):** `MAX_SEQ` is 2^31 - 1. `hbSeqOf` returns absent, an integer, or `corrupt`; negative, string, exponent, leading-zero, empty, oversized or 11 to 15 digit tokens are corrupt, never absent. `decideBoot` ignores a corrupt mirror counter, or one more than `SEQ_JUMP` (1,000,000) past IndexedDB's seq: IndexedDB wins, no import, and the mirror is rewritten; its old text is first kept as a `pre-reconcile` snapshot when it differs from what IndexedDB holds (so it is not re-imported or re-snapshotted on every boot). `canFastBoot` refuses it. `writeDoc` treats a `meta.seq` that is not an integer or is above `MAX_SEQ` as corrupt (read-only, nothing written) and aborts the transaction if the new seq would exceed it. A sidecar `idbSeq` above it is ignored. A file can never set a counter (dropped by the validator). **Export in the corrupt state** contains no IndexedDB data (only this session's memory) and the raw mirror text is refused by the importer (it has no `_vaultfit` header): T8's restore must accept raw mirror text. **Recovery for an install where the counter already went past the bound** is read-only plus Export (an automatic renumber would break "meta.seq never goes backwards", which `expectSeq` relies on); the way out is restore into a fresh store in T8.

## Export format (T7a)
Compact JSON: `_vaultfit`, `_version` (the current schema, 2), `_exported`, `_containsHealthData: true` (a machine marker; the visible label is T7b copy, also required on the raw `.txt` export), then the six sets. No profile name in the header and none in the filename: `HomeBody_<YYYY-MM-DD>.vaultfit`, `HomeBody_partial_<YYYY-MM-DD>.vaultfit`. The plain Export in unreadable, newer or unavailable states adds `_partial: true` and `_partialReason` (`unreadable`, `newer`, `unavailable`); a partial file cannot be used with Replace, and a pre-M1 build ignores the marker and may Replace with it. `buildExport` refuses (`too-large`) output the importer would refuse for size, so the app never produces a backup it cannot restore; the raw "as found" `.txt` export stays as the way out. It also runs the validator over its own output and reports records the importer would refuse (record paths) and fields it would ignore, and still produces the file.
